# REVIEW.md

Defects found in the starter `app/main.py`. Line numbers refer to the starter file. Every "how I'd notice it" example was run against the starter code.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (L33-37) | Grace check is `int(seconds/60) > 10`, so 10:01 to 10:59 of lateness is truncated before the comparison. R2 says "strictly more than 10:00". | Shift 09:30, punch-in 09:40:01 returns 0 (R2 says 10). | Compare the exact `timedelta` with 10 minutes, then floor to whole minutes since shift start. |
| 2 | `compute_late_minutes` | Shift start is built with `punch_in.replace(hour, minute)`, i.e. on the punch-in's own calendar day. Wrong for overnight shifts (a 02:00 punch-in belongs to the shift that started at 22:00 the day before). The punch-in is also a naive server-local time, not IST. | Shift 22:00, punch-in 02:00 next day returns 0 (should be 240). | `attendance_date()` applies R1 first; `shift_window()` builds the shift start/end in IST for that attendance date. |
| 3 | `compute_work_hours` (L40-41) | Python `round()` on a float is not half-up (float error plus round-half-even). | 8h 02m 42s is 8.045 h; starter gives 8.04, R4 says 8.05. About half of all exact-tie durations are wrong. | `Decimal` arithmetic on exact microseconds, quantized with `ROUND_HALF_UP`. |
| 4 | `compute_overtime` (L44-47) | Builds an IST-aware `end` but the endpoints produce naive datetimes, so subtracting raises `TypeError` (a 500). Also: no 30-minute minimum (R3), and the end of an overnight shift is not moved to the next day. | Naive punch-out raises `TypeError`. Punch-out 18:40 for a 18:30 shift gives 10 (R3: 0). 06:40 for a 22:00-06:00 shift gives 1480 (should be 40). | Single `compute_derived()` using aware datetimes, `shift_window()` for the real shift end, and the 30-minute floor. The starter helpers were not reusable as written. |
| 5 | `MongoClient(...)` (L22) | Default PyMongo returns naive datetimes; they get mixed with aware ones and with server-local `datetime.now()`. | `TypeError: can't subtract offset-naive and offset-aware datetimes`. | `tz_aware=True`; all instants are UTC-aware and only converted to IST for date and shift maths. |
| 6 | `EmployeeIn` / `PunchInIn` (L53-66) | No validation. `emp_code`, email, `HH:MM`, `joined_on` and lengths are unchecked, `shift_start == shift_end` is allowed. `punched_at` accepts seconds, negatives, floats and numeric strings. `status` accepts anything, including `ABSENT`/`LEAVE`. | `POST /employees` with `{"emp_code":"x","name":"","email":"nope","joined_on":"not-a-date","shift_start":"99:99"}` succeeds. `punched_at=1783312500` (seconds) is accepted. | Pydantic constraints from the OpenAPI contract: strict int in the epoch-ms range, real calendar dates, `HH:MM` pattern, status enums. All give 422. |
| 7 | `create_employee` (L77-85) | Check-then-insert race and no unique index, so parallel creates all get 201 and duplicates are stored. `created_at` is naive local time and is returned as a datetime (an ISO string), not epoch ms. | Fire 10 identical POSTs in parallel; several return 201. | Unique index on `emp_code` created at startup; `DuplicateKeyError` becomes 409. `created_at` stored as UTC and returned as epoch ms. |
| 8 | `list_employees` (L88-96) | `skip = page * page_size` (page 1 skips the first page). `total` counts the whole collection instead of the filtered set. No sort. No bounds on `page`/`page_size`. | `GET /employees?page=1` skips the first 20 employees. `?department=Sales` reports the all-company total. `page_size=1000000` is accepted. | `skip = (page-1)*page_size`, `count_documents(filter)`, sort by `emp_code`, `page >= 1`, `1 <= page_size <= 100`. |
| 9 | `punch_in` (L99-103) | Unknown employee gives `emp = None`, then `emp["shift_start"]` raises `TypeError`, a 500 instead of 404. | `POST /attendance/punch-in {"emp_code": "NOPE"}`. | Explicit 404 before anything else. |
| 10 | `punch_in` (L102) | `datetime.fromtimestamp(ms / 1000)` is naive server-local time. The attendance `date` therefore depends on the server's time zone, not IST, and there is no overnight rule (R1). `punched_at=0` is treated as "missing" by the truthiness test. Milliseconds are not truncated to whole seconds. | Run on a UTC server: a 09:00 IST punch-in is dated correctly but a 02:00 IST one lands on the previous day. | `from_ms()` (UTC, truncated to the second) and `attendance_date()` (IST date plus the overnight rule). `punched_at is not None` check. |
| 11 | `punch_in` (L104-118) | Check-then-insert race and no unique `(emp_code, date)` index. Two simultaneous requests both pass the `find_one` and both insert. | Two parallel punch-ins for the same employee and day both return 201. | Unique index on `(emp_code, date)`; the insert is the check. `DuplicateKeyError` is 409. |
| 12 | `punch_in` response (L119-121) | Returns `id` (the ObjectId, which the contract says never appears) and raw datetimes (ISO strings) instead of epoch ms. | Response contains `"id": "65f..."` and `"punch_in": "2026-07-06T04:00:00"`. | `record_out()` builds the response explicitly (epoch ms, no ids, defaults for legacy fields). |
| 13 | `list_attendance` (L144-150) | `list(find(q))` loads the whole collection into memory, sorts in Python and slices. No index. Sort is by `date` only, with no `emp_code` tiebreak. | About 100k records: slow and memory heavy; page order is unstable between equal dates. | Server-side `sort/skip/limit` backed by indexes; sort is `date desc, emp_code asc`. |
| 14 | `list_attendance` (L125-143) | `page=0` or negative gives a negative slice start and wrong data. `page_size` is unbounded. `date_from > date_to`, bad dates and unknown `status` are not rejected. | `GET /attendance?page=0` returns an empty or odd page; `date_from=2026-07-09&date_to=2026-07-01` returns 200. | Query validation (422) for all of these. |
| 15 | `list_attendance` output | Legacy documents without `history` / `half_day` are returned as-is, so the response violates the schema. | Fetch a legacy record such as sample #9. | `record_out()` defaults missing `history` to `[]` and `half_day` to `false`. |
| 16 | `/health` (L72-74) | Always returns ok, even when MongoDB is down. The contract wants 503. | Stop MongoDB; `/health` still returns 200. | `db.command("ping")`; `PyMongoError` becomes 503. |
| 17 | No indexes at all | The contract requires idempotent index creation at startup. Without them the unique guarantees above do not exist and lists/analytics scan the collection. | `explain` shows COLLSCAN. | `ensure_indexes()` in the app lifespan. |

## Looked at and decided it is not a defect

- `load_dotenv()` (L20): the default is `override=False`, so real environment variables already win over `.env`, as required.
- `IST = timezone(timedelta(hours=5, minutes=30))`: correct.
- `doc.pop("_id", None)` after `insert_one`: correct (PyMongo adds `_id` to the dict in place); the problem is the separate `id` field in #12.
- Plain `def` endpoints with the synchronous PyMongo client: FastAPI runs them in a thread pool, so concurrent requests are fine.
- The 409 pre-check in `create_employee` / `punch_in` is fine as a fast path, but not as the guarantee (#7, #11).
- Default `shift_start` 09:30 and `shift_end` 18:30 match the contract.
